# Visual-system board contract

Use a compact visual synthesis to show how the proposed or approved system appears on this website. Include only relevant sections. Label an absent decision `not yet decided`; label an irrelevant application `not applicable` with a short reason. This is not a checklist of assets the project must invent.

## Composition and source of truth

Place a short thesis and status at the top, followed by visual examples rather than walls of prose. Use a short set of descriptive qualities tied to visible decisions. Show a homepage/entry composition, a secondary or content view if present, and a mobile composition. A small one-page site can use one board; split an overflowing board into a small navigable set instead of shrinking everything to unreadable size.

Link directly to the brief/journeys, relevant page briefs and `DESIGN.md`. Exact values and reusable usage rules live in `DESIGN.md`. Swatches, labels and styles on the board are derived displays of those values. Note the source revision/hash. Keep filenames and navigation accessible.

An HTML board may use local inline CSS and embedded or relative project assets, without a build or external service. Use neutral framing around the project examples so the presentation wrapper does not become a new brand direction. Capture a browser view or render of the board for review when tools allow. Ensure viewers can actually open linked assets; private absolute machine paths are not portable deliverables.

## Brand identity

Show the existing logo/wordmark and permitted usage, clear space and background variants if defined. Otherwise state that no approved logo exists. A temporary text treatment is a proposal, not a newly confirmed identity.

Include a supplied or explicitly proposed tagline/core message, brand essence/values and personality only when grounded in the project. Distinguish confirmed brand facts from the agent's proposed interpretation.

## Color system

Show primary/secondary colors with exact values and assigned roles, tonal variations, approved text/surface/action combinations, and any gradients with exact stops and direction. Link contrast guidance and measurements in `DESIGN.md`. An accent color cannot serve every role simply because it looks distinctive.

## Typography system

Show actual font families, headline/subheadline/body/caption examples using relevant copy, scale, weight, line height and usage. Include how font fallback and longer text affect composition. Use only fonts available for the project or mark sourcing/licensing as pending. Do not assume a font is bundled because its name appears in a document.

## Visual language

Curate a few inspected reference excerpts or source links with the transferable principle, not a collage for imitation. Show image subject, crop, texture, illustration style, composition and tone using available assets. Explain explicit anti-references and brand-specific pitfalls.

Common failure symptoms to challenge when ungrounded: a stock gradient hero, floating decorative shapes, a logo strip without clients, interchangeable bento cards, repeated pill badges, or excessive motion masking thin content. These are not universal bans: retain a pattern when project evidence and approved direction justify it. Distinctiveness must survive removal of the logo and color accent.

## Website applications

Show the relevant homepage hero/entry view, navigation and page rhythm, case-study/content treatment if required, calls to action and contact/completion path, and mobile adaptation. Use the actual site's content hierarchy and signature move. A hero plus swatches does not demonstrate a multipage visual system.

## Layout system

Demonstrate grid/container rules, spacing rhythm, content/image proportions, page patterns and meaningful responsive changes. Annotate where composition changes rather than merely shrinking. Show long text, real image proportions and narrow-width navigation where these are risks.

## Interface components

Show only components used by the site: buttons, cards, navigation, fields/controls as relevant. Include focus, hover, active, disabled, loading, error and success states when applicable; explicitly mark states that do not exist. Touch interaction must not depend on hover. Put behavior and acceptance in page briefs, exact treatment in `DESIGN.md`.

## Brand applications

Include social graphics, campaign assets, business cards, presentations or packaging only when the actual project needs them. Otherwise mark this section not applicable. These examples should demonstrate the same system, not expand the scope.

## Iconography, patterns and micro-details

Show icon source/style/usage, recurring shapes and graphic elements, borders, shadows, reflections, texture and depth. Show a short motion storyboard or working sample when timing is essential. State reduced-motion behavior, keyboard and touch alternatives, and the reason motion helps the visitor. Static imagery cannot verify animation quality.

## Board acceptance

A reviewer can recognize the thesis in page applications, read all labels, trace values to `DESIGN.md`, distinguish real assets from placeholders, compare desktop and mobile composition, and identify unresolved decisions. Record what was actually rendered and inspected, including fonts and assets unavailable during inspection.
